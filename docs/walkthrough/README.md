# The walkthrough

Every screen a user touches, in order, photographed from a real browser against
a real stack. Regenerated by:

```bash
./scripts/dev/ensure-services.sh
psql "$TEST_DATABASE_URL" -f scripts/dev/seed-walkthrough.sql
node scripts/dev/smtp-sink.mjs &                        # :1025, accepts and discards
SMTP_URL=smtp://127.0.0.1:1025 \
  pnpm --filter @stakeam/api start &                    # :3001
pnpm --filter @stakeam/web start &                      # :3000
pnpm --filter @stakeam/web exec playwright test walkthrough
```

The mail sink is not optional. The API refuses to claim it sent a verification
code when no channel took it, so an environment without a transport cannot
complete Tier 1 — which is true of a real deployment too, and is the point.

The spec is `apps/web/e2e/walkthrough.spec.ts`. Each step asserts the one fact
that would make it a lie if it were false, then screenshots the result — so
these images cannot drift from a passing suite without the suite going red.

The run owns these folders: it clears its own numbered shots before writing new
ones. Without that the claim above was not true. Step numbers are part of the
filenames, so inserting a step renumbers everything after it and leaves the
previous run's files behind under their old numbers — three generations had
piled up, fifty files in a folder that holds twenty-two, several of them
photographs of screens as they were two changes ago.

## What the walkthrough found

Every item below was found by _looking at the product_, not by a failing unit
test — which is the argument for doing this at all. All are fixed in the same
change unless marked otherwise.

**1. The production image served no `public/` directory.** `output: standalone`
traces code, not the two directories Next serves as-is. `/manifest.json` and
`/sw.js` returned **404** in the image: the PWA was silently uninstallable and
the offline shell never registered, while every local check passed because
`next start` serves `public/` automatically. Fixed by copying `public/` in the
Dockerfile — and by pointing `pnpm start` at the standalone server, so what
runs locally and in CI is the thing that ships.

**2. The sell sheet promised more money than it paid.** It quoted
`shares × price` under the words "You receive" — linear where the engine uses a
cost curve, and with no mention of the early-exit fee the API withholds. The
sheet now computes gross from the same cost function, itemises the fee, and
shows the net; the walkthrough asserts `gross − fee = net` to the kobo.

**3. There was no way to see or sell a position.** The ticket never showed what
you held; selling existed only as a toggle inside the buy sheet. §7.2d's
position panel now shows holdings marked to market with a way out.

**4. The ticket told funding markets their event had started.** A fall-through
default in the closed-trading copy. (Fixed in the previous change; the
walkthrough is what would have caught it.)

**5. Negative money rendered as `₦-500.00`.** Sign inside the currency. Wallet
history is mostly debits, so this was on nearly every row.

**6. Starter balance and verification bonus were both labelled "Bonus".** Two
identical rows for two different things on every new account. The ledger already
distinguished them by ref; the screen was not reading it.

**7. The front door led with an empty market.** The hero took the first live
market rather than the busiest, so a stranger's first impression could be a pot
of ₦0.

**8. A queued trade lost its take, and the sheet said nothing.** §11's queue
answers `202 accepted` when a market is busy rather than holding the connection
— and the HTTP handler wrote §2.15a's reason only on the path where the trade
had already filled, so a deferred trade's reason was dropped on the floor, for
ever, precisely under the load that makes the queue defer. The take is now
written by whoever executes the trade (inline or worker), immediately after the
trade row and before the fill is announced, so it always carries the position
that trade created. The sheet no longer treats `202` as a fill either: it says
"Order placed — confirming…" and polls the status endpoint until the trade
exists or the refusal does. Found by making a submit slow enough to lose the
race — the e2e journey had been navigating on the click, which measured its own
timing rather than the product, and went red on CI the first time a runner was
slow.

**9. The verification code was readable through the session it was verifying.**
`contact_verification` went out on the `in_app` channel as well as email and
SMS, and the inbox endpoint is authenticated by exactly the session trying to
prove itself. Somebody who signed up with an address they did not own could
read their own code out of the app and take Tier 1 — the signup bonus, market
creation, leaderboards, prize eligibility. A code that travels back down the
channel it is verifying is not a second factor. In-app is gone from that
notification type; the row is still written for the channels that were tried,
because "we told them" has to stay checkable.

**10. A code that reached nobody was reported as sent.** With no `SMTP_URL` and
no `TERMII_KEY` — the state of a fresh deployment — the API answered
`{"sent": true}` and the person waited on an inbox that would never fill.
Delivery is best-effort everywhere else by design (a market must settle whether
or not an SMS gateway is up), but a verification code with nowhere to go is a
signup that cannot finish. It now returns 503 with a message the screen shows,
revokes the unusable code so the resend cooldown does not hold a retry against
the operator's fix, and logs the failure per channel. The API also says so at
boot rather than waiting for the first user to find out.

**11. A taken email answered with a database error.** Signing up on an address
that already had an account showed the person

```
Invalid `prisma.user.create()` invocation:
Unique constraint failed on the fields: (`email`)
```

The cause was one line: the signup and login handlers caught _everything_ and
forwarded `error.message` to the browser, so any unexpected failure became a
400 carrying its own internals — unreadable to the person it was shown to, a
free description of the schema to anyone else, and a disguise that kept real
failures out of the error rate by dressing them as user mistakes. Refusals now
travel verbatim because they are written for a person; anything else is logged
and answered generically. §2.7's one-account-per-contact clash is turned into a
sentence with a next step: "an account already uses that email — log in
instead, or use another address."

**12. There was no way to choose a shelf.** §7.1's two shelves were two stacked
sections and nothing else — fine on a desktop, wrong on the phone this product
is used on, where one full shelf of cards pushes the other clean off the screen
and the second reads as missing rather than as further down. There are chips
now: All · Official · Community, each carrying a count, so an empty shelf
answers for itself instead of making you tap to find out. The choice lives in
the URL, so a shelf is linkable and survives a reload, and the page stays a
server component.

**13. `pnpm start` ran a server the deployment never uses.** Next warns that
`next start` does not support `output: standalone` on every boot. That mismatch
is how (1) survived.

## Viewports

Both sets are regenerated by the same run: `desktop/` at 1280×720 and `phone/`
at 393×851, the size most Nigerian traffic arrives on. §5's Phase 2 gate is
"full market runs on a phone", and the layouts were mobile-first in intent but
had only ever been looked at wide. All fourteen steps pass on both, and no page
scrolls sideways at phone width.

## The auth screens on a phone

`auth-signup.png` and `auth-login.png` in each viewport folder, checked by
`apps/web/e2e/auth-screens.spec.ts`. Looking at them at 360px found four things
that were fine on a desktop and not on a phone:

- **The 18+ checkbox was a 16px tap target — and it gated the only button on
  the screen.** You could not create an account on a phone without hitting it.
  The whole row is the target now, and the box clears 44px.
- **Both forms were anonymous.** No wordmark, no way back to the front door.
  Someone arriving from a shared link met a password box belonging to nobody.
- **The password could only be typed blind.** Ten-plus characters on a soft
  keyboard with autocorrect is a real reason people abandon a signup; there is
  a labelled Show/Hide toggle now.
- **The forms were vertically centred**, which wasted the top third of a phone
  screen and moved the fields out from under a thumb when the keyboard opened.

A fifth came out of the fix: putting the reveal button inside the `<label>`
made the input's accessible name "Password Show password At least 10
characters". The label is bound by `htmlFor` now, so a screen reader hears
"Password" and the hint arrives through `aria-describedby`.

Login also says plainly that password recovery does not exist yet and points at
support, rather than offering a link that goes nowhere.

## Known limits of this walkthrough

- **The community create → fund → resolve arc stops at the wizard.** Market
  review calls the question engine, which has no API key here. The arc is
  covered at API level in the integration suite; it needs a staging key to be
  proven through the UI. Tracked in `docs/launch-checklist.md`.
- **Settlement is driven through the admin API, not the admin console.** The
  two-person resolution path is exercised with real staff roles and the real
  dispute-window refusal, but the browser steps check the _trader's_ side of it.
- **No real handset.** A phone-sized viewport in Chromium is not a phone: it
  says nothing about touch targets under a thumb, or about the app on a bad
  connection.
- **The dispute window is wound back with SQL**, not waited out. The window
  itself is real: finalising before it closes is refused, which is why that line
  exists.
